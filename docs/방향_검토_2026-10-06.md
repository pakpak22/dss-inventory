# 방향 검토 — 「현황표는 재고관리 기준」이 확정된 뒤 (2026-10-06)

결정(사용자 ↔ 최희만): **부품 현황표(부품 목록·수량)의 기준은 재고관리 시스템이다.** A/S 는 그것을 가져다 쓴다.
A/S 재고 기능 사본을 읽은 결과(`AS스냅샷_비교_2026-10-06.md`)와 함께 지금 방향을 다시 본 것.

## 1. 결론

지금 설계·코드는 그 결정과 맞는다. 바꿀 것은 없고, **잇는 자리**를 미리 정해 두면 된다.

- 정본이 되려면 필요한 것 셋 — ① 바뀌지 않는 식별자(No.) ② 수량의 근거(원장) ③ 누가 언제 바꿨나(변경 이력) — 가 조각 2·3·4 에 전부 들어 있다.
- A/S 가 가져가는 길(API)은 이미 만들어 두었고 보류 중이다. A/S 의 부품 고르개가 받는 다섯 칸(`id·partName·partSpec·drawingNo·kyosanPartNo`)이 우리 API 의 `no·name·name2·drawingNo·kyosanPartNo` 와 1:1 이라 그쪽 화면 코드는 거의 안 바뀐다.

## 2. 두 시스템이 갈라져 있어 미리 정해야 할 것 (🔴 최희만과)

| | A/S 지금 | 우리 | 정할 것 |
|---|---|---|---|
| 부품의 단위 | 이름 하나에 소유 넷이 버킷 | **소유마다 다른 No.** (같은 품명이 16묶음) | 견적서·O/H 템플릿·수리 건 사용 부품이 가리키는 것이 **No.** 인가 **품명 묶음**인가. 견적서는 소유를 안 보므로 묶음이 편할 수 있다 → 그러면 API 에 `묶음 키`(품명+품명2+도번) 를 더 내준다 |
| 부품 속성 중 A/S 에만 있는 것 | 작업비·단가(일반/O/H)·한계수량·O/H 템플릿 | 공급가·견적가만 | 작업비·O/H 단가·한계수량은 **A/S 가 자기 표에 우리 No. 를 열쇠로** 들고 있으면 된다(견적용 속성이지 재고가 아니다). 견적가는 우리 것을 그 시점 값으로 복사(REQUIREMENTS 8절) |
| A/S 의 부품 등록·수정 화면 | 있음 | 정본은 여기 | 전환일 이후 A/S 쪽 등록·수정은 **잠근다**(최희만). 두 곳에서 고치면 정본이 둘이 된다 |
| A/S 의 원장(stock_transactions) | 있음(자료는 버리기로) | 정본 | 전환일 이후 A/S 는 수량을 쓰지 않는다. 불출이 실제로 일어나면 **우리 원장**에 떨어져야 한다 → 4절 |
| 삭제 | 휴지통·복원 | 소프트 삭제, 되살리기 없음 | A/S 가 우리 목록을 미러링하면 **지워진 부품도 알아야** 자기 참조를 정리한다 → API 에 `includeDeleted=1` 또는 `deleted: true` 줄을 더한다(지금은 빠진다) |
| 수량 변경의 시각 | — | `updatedAt` 은 부품 정보 수정만 | A/S 가 `since=` 로 증분 동기화할 때 수량은 매번 읽어야 한다(API.md 에 적어 둠). 수량도 증분으로 받고 싶으면 `balances_updated_at` 을 더한다 |

## 3. 그대로 가는 것 (A/S 를 보고도 바꾸지 않을 것)

- 결재선 없음, 부품 요청은 나중에·결재 없이. (README 1, REQUIREMENTS 7절)
- 소유 셋·화면 `KYOSAN`, 위치 없음, 분류 enum + 항목 표, 기록 9종.
- 주문 판단은 한계수량·부족 배지가 아니라 **연도별 사용 수량**(조각 5).
- 휴지통 없음. 삭제는 기록 없는 부품만.
- 우리 화면 규약(머리말형, zinc, 목록은 브라우저에서 거름).

## 4. 반출 신청 → 우리 원장, 연결 길 (최희만이 고른다. 어느 쪽이든 조각 4 코드는 그대로 쓰인다)

1. **당분간**: 가져가는 사람이 재고 화면(휴대폰)에서 직접 기록. 1차 범위 그대로. A/S 요청 화면은 "요청"만 남고 수량은 안 건드린다.
2. **A/S 가 우리 기록 통로를 부른다**: `POST /api/v1/entries`(API.md 4-1 제안). A/S 의 불출 단추가 우리 원장에 사용 한 건을 쌓는다. 인수번호는 우리가 다시 확인.
3. **요청 화면을 재고로 옮긴다**: 나중에 붙이기로 한 「부품 요청·확인」. A/S 의 상태 7종·멱등 키 설계가 본보기.

추천은 1 → 2. 2 는 통로 하나만 더 열면 되고, 3 은 그 뒤에 해도 늦지 않다.

## 5. 지금 당장 손볼 것 (우선순위)

1. 보강 제안 셋(원장 CHECK, 부품 수정 동시성, 이력 있는 부품 삭제 단추) — 사용자 답 대기.
2. API 에 지워진 부품 표시(`deleted`)와 묶음 키 — 최희만이 2절 첫 줄을 정한 뒤.
3. 조각 5(과거 기록 가져오기 + 연도별 사용 수량) → 6(인쇄·엑셀) → 7(한 벌 자동 갱신) → 전환.
4. 전환일 전에 최희만: 야간 백업에 DB·업로드·틀 두 벌 포함, A/S 부품 등록·수정 잠금, A/S 가 우리 API 로 전환.

## 6. 최희만에게 보낼 질문 (짧게)

1. 견적서·O/H 템플릿·수리 건 사용 부품이 가리킬 것: 재고 No. 인가, 품명 묶음인가.
2. 작업비·O/H 단가·한계수량·O/H 템플릿은 A/S 에 남기고 우리 No. 로 잇는 것이 맞는가.
3. 전환일 이후 A/S 의 부품 등록·수정·원장 쓰기를 잠그는 시점과 방법.
4. 반출 신청 → 우리 원장 연결은 4절의 1 → 2 순서로 가도 되는가.
5. 저장 뒤 화면에 남는 방식(2026-09-17 결정)을 재고관리에도 적용할지.

## 8. 사용자에게 물을 것 (답변3 에서 생긴 것)

1. 「왜 따로 두었는지」 글자: 비고 첫 줄을 그대로 내줄지, 부품에 짧은 **「용도 구분」 칸**(예: YAC사양 / 개조용 / T/C用)을 새로 둘지. 칸을 두면 등록·수정 화면과 API 에 한 칸 늘고 마이그레이션 하나.
2. 한계수량: 담당자 권고대로 「쓰지 않는다」로 적어도 되는지.

### 8절의 답 (사용자, 2026-10-06)

1. **비고로 둔다.** 용도 구분 칸은 만들지 않는다. 사람이 알아보면 되는 글자이고, A/S 고르개는 API 의 `note` 를 그대로 보여 주면 된다 → 최희만에게 "구분 글자는 비고 칸, API 의 `note`" 로 답한다.
2. **한계수량은 쓰지 않는다.** 전환과 함께 죽는 값. 재고관리로 가져오지 않고, A/S 에도 남기지 않는다(담당자 권고 그대로).
