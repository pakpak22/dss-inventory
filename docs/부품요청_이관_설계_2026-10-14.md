## 4. 🔴 두 시스템이 만나는 지점 셋

### ① A/S → 재고 관리 : 요청 만들기
수리 건 상세에서 [부품 인수 요청]을 누르면 재고 관리에 요청이 생긴다.
🔵 **길이 이미 있다** — 재고 관리의 `stock_requests` 는 「신청 → 담당자 확인 → 반출」이고
`stock_entries.intake_number`(인수번호 · D+6자리) 칸을 들고 있다.
그리고 `intake_unverified` 칸이 **「A/S 가 응답하지 않아 인수번호를 확인하지 못한 채 저장함」**
을 위해 만들어져 있다 — 이 연결을 내다보고 만든 구조다.

### ② 재고 관리 → A/S : 인수번호 확인
재고 관리가 인수번호로 고객사·모델을 묻는 통로가 **이미 설계돼 있다**
(`AS_LOOKUP_URL` · `src/lib/stock/intake-lookup.ts`).

### ③ A/S → 재고 관리 : 부품 조회
`GET /api/v1/parts` 가 **이미 있다**. 🔴 다만 **보류 중**이라 운영 토큰
(`INVENTORY_API_TOKEN`)이 아직 없다 — 2026-10-14 설치 때 넣지 않았다.

🔴 **A/S 쪽에는 재고 관리를 부르는 코드도 환경변수도 하나도 없다** (실측 0건).
통로를 여는 것이 별도 조각이다.

## 5. 🔴 정해야 할 것 — 요청 모양이 다르다

A/S 와 재고 관리의 「요청」이 **같은 것이 아니다.**

| | A/S `inventory_part_requests` | 재고 관리 `stock_requests` |
|---|---|---|
| 모양 | 머리 1 + 줄 N (부품마다 한 줄) | 요청 1개 = `payload`(JSON) 한 덩어리 |
| 부분 불출 | **된다** (`issued_quantity`, `request_issues` 표) | 확인하면 한 번에 원장으로 |
| 상태 | PENDING 등 + 별도 승인 표 3개 | PENDING·CONFIRMING·CONFIRMED·REJECTED·CANCELLED |
| 수리 건 | `repair_case_id` FK | `intake_number` 글자 |

### ✅ 정해졌다 (2026-10-14 사용자) — **재고 관리 쪽을 늘린다**

🔴 **이 절이 처음에 적은 전제가 틀렸다. 2026-10-14 조사로 바로잡는다.**

#### 🔵 「줄 단위」는 **이미 있다**

위 표의 「요청 1개 = `payload` 한 덩어리」는 **저장 모양**을 말한 것이고,
**그 덩어리 안에 줄이 N개 들어 있다.**

- 확인을 거치는 세 종류(USE·LOAN·DISPOSE)가 전부 `lines: Line[]` — `src/lib/stock/form.ts:30-37`
- **최대 50줄** — `form.ts:47`. 같은 부품 두 줄은 막는다(「한 줄에 수량을 합치십시오」)
- 화면도 지원한다 — `EntryForm.tsx:402` 의 「부품 더 넣기」
- 🔵 **원장도 이미 줄 단위다** — `LineSpec`(`ledger.ts:44-51`) · `writeEntry(tx, head, lines[], actor)`(`ledger.ts:102`)

→ **새로 만들 것은 「줄」이 아니라 「부분 불출」 하나뿐이다.**

#### 🔵 경계는 **한 줄**이다

```
[요청 쪽 — 늘린다]            recordEntry(EntryInput, Actor, RecordOptions)       [원장 — 안 건드림]
stock_requests · payload        ← src/lib/stock/ledger.ts:205                     stock_entries
createRequest · confirmRequest                                                    stock_transactions
화면 · 상태 · 요약              🔴 유일한 호출 지점: src/lib/stock/requests.ts:101  stock_balances · ledger.ts 전부
```

확인될 때 `requests.ts:101` 이 `payload` 를 **풀지 않고 통째로** `recordEntry` 에 넘긴다.
그 한 줄에서 **「요청 수량 lines」 대신 「불출 수량 lines」로 만든 `EntryInput`** 을 넘기면
원장은 그것이 부분인지 전부인지 **알 필요가 없다.** 타입도 그대로다.
🔵 사용자가 못 박은 **「수량 변경 기록은 그대로 유지」가 타입으로 지켜진다.**

#### ✅ 분할 불출 — **여러 번** (2026-10-14 사용자)

> 「여러 차례 나눠서 주기도 하고 **기다리기도** 한다」

→ 요청이 **열린 채 남아** 있어야 한다. 한 번 주고 닫는 모양이 아니다.

🔴 **걸림돌**: `stock_entries.request_id` 에 UNIQUE 가 걸려 있다
(`src/db/schema/stock.ts:82` · 「같은 신청이 두 번 쓰이지 않게」).
그대로면 **한 신청에서 원장 건이 두 번 나올 수 없다.**

🔵 **원장을 안 건드리고 푸는 길** — 이렇게 한다:

```
요청 ──┬── 1회차 불출 ── 원장 건 (request_id 는 null)
       ├── 2회차 불출 ── 원장 건 (request_id 는 null)
       └── 남은 수량 … 요청은 열려 있다
          ↑ 요청 쪽 중간 표(stock_request_issues 류)가 회차와 entry_id 를 들고 잇는다
```

- `stock_entries.request_id` 는 **nullable** 이고(`stock.ts:73`)
  `RecordOptions.requestId` 도 **선택**이다(`ledger.ts:200`) → 비워 넣으면 UNIQUE 에 안 걸린다
- 🔵 **선례가 있다** — USE 의 「실제 수량이 다릅니다」가 만드는 ADJUST 건이
  `request_id` 를 안 붙인 채 들어간다(`ledger.ts:252` vs `:269`)
- 🔴 **대가**: 원장 건 → 요청으로 거슬러 가는 길이 중간 표를 한 번 거친다. 화면에는 안 보인다
- 🔴 **일관되게 전부 null 로** 한다. 첫 회차만 붙이고 나머지를 비우면 읽는 사람이 헷갈린다

#### 🔴 상태가 하나 늘고, 그 파급이 다섯 곳이다

「**일부만 나갔고 아직 남음**」 상태가 필요하다.
✅ **대기로 센다** — 아직 줄 것이 남아 담당자가 계속 봐야 한다.

🔴 상태를 늘리면 **조용히 틀리는 곳 다섯** (전부 `src/lib/stock/requests.ts` 와 알림):
`listPendingRequests:188` · `listRecentDecidedRequests:198` · `countPendingRequests:212`(머리말 배지) ·
`summarizePendingRequests:232` · `src/lib/notifications/bell-items.ts:41-42`
→ 여기를 안 맞추면 **「대기 N건」 배지와 알림 종이 거짓말을 한다.** 원장은 안 깨지므로 시험으로 안 잡힌다.

#### 🔴 `payload` 와 줄 표가 공존하면 — 진실을 한 곳으로

줄 표를 더하면 같은 사실이 `payload` 와 줄 표 **두 곳**에 적힌다.
`requests.ts:101·157·205` 가 `payload` 를 `as unknown as EntryInput` 로 **무검증 캐스팅**한다.
→ **「원장에 넘길 `EntryInput` 을 만드는 곳」을 한 군데로 못 박는다.**
`requests.ts:101` 직전에 **「줄 표 → EntryInput」 변환 함수 하나**를 두고
**그것만이 원장으로 가는 길**이 되게 한다.

## 6. 🔴 정해야 할 것 — 단가가 둘인데 받을 곳은 하나

A/S 는 단가 표가 **둘**이다: `part_unit_prices`(일반) · `part_overhaul_unit_prices`(O/H).
견적서 고르개가 OH 줄이면 O/H 단가를, 아니면 일반 단가를 넣는다.
🔴 **O/H 단가가 없으면 일반 단가로 대신 채우지 않고 빈칸으로 둔다**(그렇게 정해져 있다).

재고 관리에는 `parts.quote_price` **하나**뿐이다.

사용자 요청: 「부품별 단가는 재고 현황의 **견적가**를 가져온다」

### ✅ 정해졌다 (2026-10-14 사용자) — **O/H 단가는 「O/H 부품 템플릿」에만 둔다**

| | 어디서 | 뜻 |
|---|---|---|
| 일반 단가 | `parts.quote_price` (재고 현황의 **견적가**) | 부품마다 하나 |
| **O/H 단가** | 🔴 **O/H 부품 템플릿 쪽에** | 부품 자체가 아니라 **그 템플릿에서의 값** |

🔵 `parts` 에 O/H 견적가 칸을 **더하지 않는다.** 부품 하나에 단가가 둘 붙는 모양을 피한다.
🔵 지금 A/S 의 규칙(「O/H 단가가 없으면 일반 단가로 대신 채우지 않고 빈칸」)은
템플릿 쪽에 값이 없으면 빈칸으로 두는 것으로 그대로 살린다.
