## 1. 왜 옮기나

- 2026-10-02 결정: **「부품 마스터가 재고관리로 간다」**. 그때 A/S 쪽 할 일에
  「부품 목록 연결」이 들어 있었다.
- 2026-10-13~14: 재고 관리가 NAS 에 서고 실자료(부품 319 · 과거 2,288건)가 들어갔다.
  이제 **진짜 마스터는 재고 관리**다.
- 고객사 제출용 품명(견적서에 나갈 이름)과 견적가를 쓰려면 A/S 가 재고 관리를 봐야 한다.

## 3. 옮기는 것 / 남기는 것

### 3-1. 재고 관리로 간다

| 기능 | A/S 의 표 | 재고 관리에 |
|---|---|---|
| 부품 마스터 | `parts` | 🔵 **이미 있다** (`parts`, 319개) |
| 재고 잔량 | `part_stock_balances` | 🔵 **이미 있다** (`stock_balances`) |
| 재고 원장 | `stock_transactions` | 🔵 **이미 있다** (`stock_entries`+`stock_transactions`) |
| 부품 요청 관리 | `inventory_part_requests` 외 4표 | 🟡 **비슷한 것이 있다** (`stock_requests`) — 아래 5절 |
| 승인 요청건 | `inventory_part_issue_*` 3표 | 🟡 `stock_requests.status` 로 덮을지 봐야 한다 |
| O/H 부품 템플릿 | `oh_part_templates` 외 2표 | 🔴 **없다. 만들어야 한다** |
| 부품 단가 | `part_unit_prices` · `part_overhaul_unit_prices` | 🟡 `parts.quote_price` 하나뿐 — 아래 6절 |
| 최소 수량 | `part_minimum_quantities` | 🔴 없다 |

### 3-2. A/S 에 남는다

- **수리 건 상세의 「부품 요청하기」** — 요청을 거는 입구. 사용자가 그렇게 정했다.
  다만 부품 목록은 재고 관리에서 가져오고, 만든 요청도 재고 관리에 쌓인다.
- **사용 부품** (`repair_case_used_parts`) — 수리 기록의 일부다.
- **견적서** (`quote_items`) — 품명·단가가 스냅샷이라 독립적이다.

## 4. 🔴 두 시스템이 만나는 지점 셋

### ① A/S → 재고 관리 : 요청 만들기
수리 건 상세에서 [부품 인수 요청]을 누르면 재고 관리에 요청이 생긴다.
🔵 **길이 이미 있다** — 재고 관리의 `stock_requests` 는 「신청 → 담당자 확인 → 반출」이고
`stock_entries.intake_number`(인수번호 · D+6자리) 칸을 들고 있다.
그리고 `intake_unverified` 칸이 **「A/S 가 응답하지 않아 인수번호를 확인하지 못한 채 저장함」**
을 위해 만들어져 있다 — 이 연결을 내다보고 만든 구조다.

### ② 재고 관리 → A/S : 인수번호 확인
재고 관리가 인수번호로 고객사·모델을 묻는 통로가 **이미 설계돼 있다**
(`AS_LOOKUP_URL` · `src/lib/stock/intake-lookup.ts`).

### ③ A/S → 재고 관리 : 부품 조회
`GET /api/v1/parts` 가 **이미 있다**. 🔴 다만 **보류 중**이라 운영 토큰
(`INVENTORY_API_TOKEN`)이 아직 없다 — 2026-10-14 설치 때 넣지 않았다.

🔴 **A/S 쪽에는 재고 관리를 부르는 코드도 환경변수도 하나도 없다** (실측 0건).
통로를 여는 것이 별도 조각이다.

## 5. 🔴 정해야 할 것 — 요청 모양이 다르다

A/S 와 재고 관리의 「요청」이 **같은 것이 아니다.**

| | A/S `inventory_part_requests` | 재고 관리 `stock_requests` |
|---|---|---|
| 모양 | 머리 1 + 줄 N (부품마다 한 줄) | 요청 1개 = `payload`(JSON) 한 덩어리 |
| 부분 불출 | **된다** (`issued_quantity`, `request_issues` 표) | 확인하면 한 번에 원장으로 |
| 상태 | PENDING 등 + 별도 승인 표 3개 | PENDING·CONFIRMING·CONFIRMED·REJECTED·CANCELLED |
| 수리 건 | `repair_case_id` FK | `intake_number` 글자 |

### ✅ 정해졌다 (2026-10-14 사용자) — **재고 관리 쪽을 늘린다**

`stock_requests` 에 **줄 단위**와 **부분 불출**을 더한다. 새 요청 표를 또 만들지 않는다.

🔴 **「수량 변경 기록」 기능은 그대로 유지한다** (사용자가 못 박았다).
즉 `stock_entries` · `stock_transactions` 로 쌓이는 원장과 그 화면은 **한 글자도 안 건드린다.**
늘리는 것은 **요청 쪽(`stock_requests`)뿐**이고, 확인된 요청이 원장에 쓰이는 지금 길은 그대로다.

→ 늘릴 것(안):
- 요청 줄 표 하나 (`stock_request_items` 류) — 부품마다 한 줄 · 요청 수량 · 소유 · 메모
- 부분 불출을 셀 칸 (`issued_quantity` 류)
- 🔵 `payload`(JSON) 는 남겨 둔다 — 지금 반출 흐름이 그것으로 돈다. **줄 표는 더하기만 한다.**

🔴 **확인할 것**: 지금 `stock_requests` 가 확인될 때 원장을 쓰는 코드가 `payload` 를 푼다.
줄 표를 더한 뒤 **그 경로가 안 바뀌는지**를 먼저 읽고 조각을 나눌 것.

## 6. 🔴 정해야 할 것 — 단가가 둘인데 받을 곳은 하나

A/S 는 단가 표가 **둘**이다: `part_unit_prices`(일반) · `part_overhaul_unit_prices`(O/H).
견적서 고르개가 OH 줄이면 O/H 단가를, 아니면 일반 단가를 넣는다.
🔴 **O/H 단가가 없으면 일반 단가로 대신 채우지 않고 빈칸으로 둔다**(그렇게 정해져 있다).

재고 관리에는 `parts.quote_price` **하나**뿐이다.

사용자 요청: 「부품별 단가는 재고 현황의 **견적가**를 가져온다」

### ✅ 정해졌다 (2026-10-14 사용자) — **O/H 단가는 「O/H 부품 템플릿」에만 둔다**

| | 어디서 | 뜻 |
|---|---|---|
| 일반 단가 | `parts.quote_price` (재고 현황의 **견적가**) | 부품마다 하나 |
| **O/H 단가** | 🔴 **O/H 부품 템플릿 쪽에** | 부품 자체가 아니라 **그 템플릿에서의 값** |

🔵 `parts` 에 O/H 견적가 칸을 **더하지 않는다.** 부품 하나에 단가가 둘 붙는 모양을 피한다.
🔵 지금 A/S 의 규칙(「O/H 단가가 없으면 일반 단가로 대신 채우지 않고 빈칸」)은
템플릿 쪽에 값이 없으면 빈칸으로 두는 것으로 그대로 살린다.
